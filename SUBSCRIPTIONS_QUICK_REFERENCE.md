# Subscriptions Implementation Summary

## What Was Added

### 1. Server-Side Subscriptions (`graphql-server/server.js`)
- Added `graphql-subscriptions` PubSub for event publishing
- Added `graphql-ws` WebSocket support
- Created `RootSubscription` GraphQL type with `userAdded` field
- Configured WebSocket server on port 4000
- **Key Code**: When `addUser` mutation runs, it publishes `USER_ADDED` event

```javascript
pubsub.publish('USER_ADDED', { userAdded: newUser });
```

### 2. Client-Side WebSocket Link (`apolloClient.ts`)
- Created `GraphQLWsLink` to handle WebSocket connections
- Used `split` to route subscriptions to WebSocket, queries/mutations to HTTP
- Configured Apollo Client with dual-link setup

### 3. Subscription Query (`operations.graphql`)
```graphql
subscription OnUserAdded {
  userAdded {
    id
    firstName
    age
    companyId
    company { id name description }
  }
}
```

### 4. Real-Time Notifier Component (`SubscriptionNotifier.tsx`)
- Uses `useOnUserAddedSubscription()` hook (auto-generated by Codegen)
- Displays toast notification when new user is added
- Animated entrance with bounce icon

### 5. Type Generation
- Codegen now generates `useOnUserAddedSubscription` hook
- Full TypeScript support for subscription data and variables

## How It Works (Flow)

```
User fills form → Clicks "Add User"
    ↓
React component calls addUser mutation
    ↓
Mutation sends to GraphQL server (HTTP)
    ↓
Server creates user in database
    ↓
Server calls pubsub.publish('USER_ADDED', { userAdded: newUser })
    ↓
WebSocket connection in browser receives message
    ↓
Apollo Client updates subscription data
    ↓
SubscriptionNotifier component re-renders
    ↓
Toast notification appears (same in all open tabs!)
```

## Key Concepts

### Subscription vs Query/Mutation
| Type | Request | Response | Use Case |
|------|---------|----------|----------|
| Query | Client → Server | One-time response | Fetch data |
| Mutation | Client → Server | One-time response | Modify data |
| **Subscription** | **Client ↔ Server** | **Continuous stream** | **Real-time updates** |

### PubSub Pattern
- **Publisher**: Server publishes events (when user is added)
- **Subscriber**: Client listens for events (SubscriptionNotifier)
- **Channel**: 'USER_ADDED' (named event)
- **Data**: Serialized as GraphQL object

## Production Considerations

1. **Message Queueing**: For high scale, use Redis instead of in-memory PubSub
2. **Error Handling**: Add retry logic for disconnected clients
3. **Authentication**: Add token verification to WebSocket handshake
4. **Filtering**: Subscribe to specific user groups (e.g., `userAddedInCompany(id)`)
5. **Rate Limiting**: Throttle subscription updates

pubsub.publish(`USER_ADDED_COMPANY_${companyId}`, { userAddedInCompany: newUser });
